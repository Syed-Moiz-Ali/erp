# PHASE 3.6 — Automatic Development and Production Environment Configuration

## Objective

Refactor the existing Flutter ERP application to use two environment files, automatically selected by Flutter build mode.

I currently use ngrok to expose my development backend.

I do NOT want to pass `--dart-define` arguments when running or building the application.

The implementation must be secure, maintainable, scalable and compatible with the existing Dio and authentication infrastructure.

## 1. Environment files

Create the following project-root files:

`.env.development`

`.env.production`

Add a suitable environment loader dependency such as `flutter_dotenv`, if not already installed.

Both files must have the same configuration schema.

Minimum fields:

- `API_BASE_URL`
- `AUTH_MODE`

Example development configuration:

API_BASE_URL=https://your-dev-tunnel.ngrok-free.app
AUTH_MODE=backend

Example production configuration:

API_BASE_URL=https://api.yourdomain.com
AUTH_MODE=backend

Do not add credentials, access tokens, refresh tokens, client secrets or encryption keys to environment files.

Keep documented placeholders until valid URLs are explicitly available.

Never invent a production endpoint.

## 2. Automatic selection

Use Flutter's compile-time build-mode constants.

Expected behavior:

- Debug (`kDebugMode`) → `.env.development`
- Profile (`kProfileMode`) → `.env.production`
- Release (`kReleaseMode`) → `.env.production`

Production configuration must be used for both Profile and Release unless an existing project requirement explicitly needs something different.

Do not introduce manual environment toggles for normal operation.

Do not depend on `--dart-define`, `--dart-define-from-file`, shell environment variables or platform-specific run arguments for selecting the environment.

Do not use runtime heuristics such as localhost detection to select an environment.

## 3. Startup initialization

Inspect the actual Flutter bootstrap and `main.dart`.

Ensure the environment file loads before:

- GetIt dependency registration
- AppConfig evaluation
- Dio client initialization
- Authentication session restoration
- Initial route resolution

Initialize Flutter bindings before loading assets.

Load the correct file asynchronously before constructing dependencies.

Handle missing, malformed and empty configurations explicitly.

Do not allow a configuration loading failure to silently activate demo mode.

Provide a safe initialization error if configuration is invalid.

## 4. Refactor AppConfig

Inspect `lib/app/app_config.dart` and existing configuration consumers.

Replace environment selection currently based on:

- `String.fromEnvironment('API_BASE_URL')`
- `bool.fromEnvironment('DEMO_AUTH')`
- `bool.fromEnvironment('ALLOW_INSECURE_HTTP')`

with the loaded environment configuration.

Remove obsolete dart-define-dependent behavior for API configuration and auth-mode selection.

Preserve unrelated legitimate compile-time Flutter settings.

Provide one centralized configuration API for:

- Active environment name
- API base URL
- Authentication mode
- Configuration validity

Avoid direct `.env` reads throughout feature modules.

Make configuration injection easy to override in automated tests.

Do not change the repository architecture.

## 5. Ngrok compatibility

My development backend is exposed through an ngrok HTTPS URL.

Requirements:

- Accept properly formatted ngrok HTTPS endpoints.
- Preserve the configured hostname.
- Do not append duplicate API path segments.
- Use the configured URL with the existing backend endpoint paths.
- Ensure the Dio base URL is constructed correctly.
- Preserve trusted-origin authorization-header protections.
- Do not disable TLS certificate validation.
- Do not blindly add ngrok-specific headers that the backend contract does not require.
- Handle connection failures, tunnel-expired responses, unexpected HTML responses and backend JSON errors distinctly.

Document that restarting a temporary ngrok tunnel may require updating `.env.development` and restarting the Flutter application.

For Flutter Web, explain and verify backend CORS configuration against the app's actual origin.

Do not try to bypass CORS in Flutter.

## 6. Security validation

Apply these rules:

- Development may use an explicitly configured ngrok HTTPS endpoint.
- Production must use HTTPS.
- Profile builds must follow production URL security requirements.
- Production configuration must not use localhost, loopback, emulator addresses, private-network HTTP or placeholder URLs.
- Invalid configuration must fail clearly.
- No fallback from production to development URLs.
- No fallback from backend authentication to demo authentication.
- No token or password in diagnostic logging.
- Authorization headers must only be attached to the configured trusted backend origin.

Explicit demo mode, if retained for internal development, must be impossible to activate accidentally in production builds.

## 7. Test environment isolation

Environment loading must not break existing widget/unit tests.

Make tests able to inject a test configuration without reading real environment files.

Do not let tests connect to the actual ngrok tunnel or production server.

Test:

- Debug mode selects development configuration.
- Profile mode selects production configuration.
- Release mode selects production configuration.
- Correct URL is injected into Dio.
- Backend AuthRepository is selected.
- Explicit demo mode works only where allowed.
- Missing environment file fails safely.
- Missing API URL fails safely.
- Malformed URL fails safely.
- Production HTTP URL is rejected.
- Production placeholder URL is rejected.
- Tokens are restricted to the configured origin.
- No automatic fallback between environments.
- No prior dart-define flags are needed for normal execution.

Do not create tests that depend on a real ngrok connection.

## 8. Build integration

Ensure `.env.development` and `.env.production` are bundled as Flutter assets, if using flutter_dotenv.

Confirm compatibility with:

- Flutter Web
- Android
- iOS
- Windows Desktop

Check project-root `pubspec.yaml` asset declarations.

Do not add Android or iOS native environment libraries unless actually necessary.

Avoid introducing separate platform-specific configuration systems.

## 9. Developer experience

Normal execution should become:

Development:

`flutter run -d chrome`

`flutter run -d windows`

`flutter run -d android`

Production:

`flutter build web --release`

`flutter build apk --release`

`flutter build windows --release`

No extra command-line environment arguments are required.

Provide safe debug-only logging of:

- Selected environment
- Selected auth mode
- Sanitized API origin
- Configuration validity

Never log credentials or authentication tokens.

Compare any failures against the known baseline.

Fix newly introduced regressions.

## Definition of Done

The phase is complete when:

- Debug automatically loads `.env.development`.
- Profile and Release automatically load `.env.production`.
- Dio uses the correct configured API URL.
- Authentication uses backend mode by default when validly configured.
- No API-related dart defines are needed.
- Invalid configuration fails safely.
- ngrok HTTPS endpoints work with the existing URL validation.
- Production cannot fall back to development or demo mode.
- Existing authentication and Department integrations remain intact.
- No new analyzer errors or test regressions exist.

Do not proceed to Employee, Shift or Attendance API integration.

**Implement the configuration changes, test them, document the results and STOP.**
