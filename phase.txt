==================================================
1. CRITICAL — ACTION PERMISSIONS MUST NOT ESCALATE VIEW SCOPE
==================================================

The current security implementation has a serious authorization problem.

Audit:

core/security/app_permission.dart

and the effective permission/scope resolution path.

Current behavior found during audit:

action permissions such as:

Inspection Edit
Inspection Complete

Material Request Edit
Material Request Print

Work Execution Perform

and similar Services action permissions

are mapped/dependent on:

*ViewAll

permissions.

This can produce dangerous behavior such as:

User has:

services.workExecutions.view = ASSIGNED

plus:

services.workExecutions.perform = granted

and the dependency system effectively provides:

services.workExecutions.viewAll

causing the scope resolver to treat the user as ALL.

THIS MUST BE FIXED.

==================================================
2. ACTION PERMISSION PRINCIPLE
==================================================

Action permissions must NEVER upgrade record visibility scope.

Example:

View Work Executions:
ASSIGNED

Perform Work:
YES

must mean:

user may perform work ONLY on Work Executions visible within ASSIGNED scope.

It must NOT mean:

user may view ALL Work Executions.

Same rule applies to:

Edit

Complete

Cancel

Print

Review

Adjust

Manage transaction actions

where object access depends on a separately scoped View permission.

==================================================
3. CORRECT AUTHORIZATION MODEL
==================================================

The authorization model must remain:

Module enabled
AND
Action permission granted
AND
View permission available
AND
record lies inside granted View scope
AND
company matches
AND
required Employee link exists where relevant.

Action permission is orthogonal to scope.

Example:

services.inspections.view = TEAM

services.inspections.complete = granted

Result:

Complete action may operate only on Inspections inside TEAM scope.

NOT ALL.

==================================================
4. PERMISSION DEPENDENCIES
==================================================

Audit:

permissionViewDependencies

AppPermission dependency mapping

effective PermissionSet calculation

or equivalent implementation.

Dependencies may establish:

Manage implies View capability exists

BUT MUST NOT assign:

ALL scope.

If an action implies View:

the implied View scope must not exceed the actual configured View grant.

Prefer:

action is usable only when a real View grant exists.

If the system requires implicit View for action grants:

derive the least privilege compatible scope,
never ALL.

Document the final approach.
