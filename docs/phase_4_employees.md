# Phase 4 Employee Management handoff

1. **Implementation.** Employee list, detail, create/edit and activate/deactivate are registered in the existing ERP shell. Search, five typed filters, five sort modes, SQL pagination/counts, a single row action menu, confirmations and unsaved-change protection work. No hard-delete feature exists.

2. **Important files.** `lib/features/employees/domain/employee.dart`, `employee_repository.dart`, `employee_access.dart`; `data/employee_tables.dart`, `employee_dao.dart`, `local_employee_repository.dart`, `employee_seed.dart`, `account_provisioning_repository.dart`, `local_account_access_guard.dart`; `presentation/bloc/employee_list_bloc.dart`, `employee_form_bloc.dart`, `employee_details_bloc.dart`; `presentation/pages/employee_list_page.dart`, `employee_form_page.dart`, `employee_details_page.dart`. Composition changes are in bootstrap/dependencies, registered_modules, navigation_resolver and app_routes. Shared additions are AppSelectField, AppSwitchField, AppDetailsGrid, AppFormGrid, AppRelatedAction, AppActionMenu and FormNavigationGuard. Employee tests are in `test/employee_test.dart` and `test/employee_widget_test.dart`.

3. **Domain model.** Immutable Freezed Employee has distinct ID/company/code, first/middle/last/display names, normalized contact identifiers, avatar reference, department/designation/manager, joining date, typed employment type/status, nullable shift/location/policy references, optional linked user ID, login enablement, timestamps and typed sync status. First name is required; middle and last names are optional to support people with a single name. EmployeeDraft and EmployeeFilter are typed and immutable. UserAccount and Employee remain separate entities. No password or token appears in an employee.

4. **Repository architecture.** Widgets use the three workflow BLoCs, which use EmployeeRepository. EmployeeDao owns SQL reads/writes; account provisioning is a separate collaborator. Reads are local-first reactive streams. Employee/account changes and a mutation containing the employee plus non-secret account configuration commit in one Drift transaction. Failed outbox insertion rolls back both records. New writes remain pending; no sender or automatic acknowledgment is installed. Writes serialize through the singleton repository, and constraints enforce company-unique codes/email/phone and unique user linkage.

5. **Drift/migration.** Schema 2 adds workforce_employees, workforce_departments, workforce_designations, workforce_accounts and workforce_seeds. Migration from schema 1 preserves the sync_outbox table and its pending mutations. Foreign keys and company/manager/filter indexes are enabled. `drift_schemas/drift_schema_v2.json` records the new schema. The existing web database worker was regenerated. Seed version markers prevent replacing edited data on restart. Twenty-five stable fixtures include Arabic names, five departments/designations, three linked demo employees and ten direct reports to the demo manager. Fixture `synced` status describes the seeded baseline, not a remote synchronization event.

6. **EmployeeListBloc.** Owns query, filters, sort, page, references, loading/busy/error and operation feedback. Search debounces 300 ms. Parameterized SQL applies scope before search/filter/count/limit/offset. Generation IDs reject stale subscriptions. Search/filter/sort reset pagination, and reactive count changes clamp an invalid page. List state survives detail/edit navigation within its branch and resets with authenticated context.

7. **EmployeeFormBloc.** One workflow supports create and edit, preloads references/account/code, retains the immutable original draft for dirty comparison, derives localized field-error codes, serializes submissions and drops duplicate submissions. Repository validation includes email/phone uniqueness, active company-owned references, past/current joining date and manager cycles. Failure retains the draft. Shared forms disable controls while saving, show inline errors and require confirmation before leaving a dirty form. Session or authorization changes bypass the dirty guard so access can be revoked immediately.

8. **EmployeeDetailsBloc.** Watches the scoped employee record and loads related reference labels and linked account information. Edits/status changes propagate from Drift, including updates with no change in row count. Not-found and unauthorized are distinct from storage failure. Safe failures show feedback while retaining an available record; storage states support retry.

9. **Scopes.** Explicit employeeViewAll gives company scope; employeeViewTeam gives direct reports through manager_id; employeeViewSelf gives the referenced employee only. A team actor with self permission may also open their own detail. Missing employee reference or view permission gives no records. Self-only employees do not see the Employees navigation/list, but their Profile can open their own employee detail. Another company is never included in a query. Create/update/deactivate grants are enforced again by the repository, independently of route/UI guards. These are frontend behavior constraints, not a replacement for future server authorization.

10. **Login linking.** AccountProvisioningRepository creates/updates a separate local account and returns its ID. Turning login off retains the link and disables the account; employee deactivation disables linked access without deleting employment history. New account records are explicitly credential-pending, and the detail page displays that state. Existing demo identities retain fixture credentials and login identifiers. Employee contacts may change independently of those credential-backed account identifiers. LocalAccountAccessGuard prevents disabled identities from logging in/restoring sessions and revokes active access on deactivation. Local role/permission changes update active session context and are applied again on restoration. Sensitive session envelopes remain in secure storage.

11. **Role restrictions.** Auth-domain grant templates define explicit permissions. AccountRolePolicy derives available roles from the actor's complete permission ceiling. All-view grants can delegate narrower team-view grants. HR can provision Employee/Manager/HR templates when its explicit grants permit them; company administrative templates require administrative grants. Super Admin is never provisioned through an Employee form. Role labels never authorize a route or operation. Account identifier conflicts return duplicate-field validation and roll back the transaction.

12. **Responsive behavior.** Compact screens use purpose-built employee cards. Medium layouts reduce table columns; expanded/large layouts show detailed workforce columns. Tables have stable sorting, horizontal safety and pagination. Forms use a centered 820 px maximum with two columns when space permits and one on compact layouts. Selection/filter panels use mobile sheets and desktop dialogs. Pages retain centralized design-system spacing, colors, typography, controls and reduced-motion-aware entrance animations.

13. **English/Arabic/RTL.** New UI strings are ARB-based. Both languages are checked at 360, 390, 430, 600, 768, 900, 1024, 1280, 1440 and 1920 px across list/details/create/edit, including validation. English/Arabic filter sheets/dialogs, search, status menus and confirmations are exercised on mobile/desktop. Identifiers render LTR within RTL pages. Business names are stored data rather than translated UI constants. Bundled Inter/Noto Sans Arabic remain unchanged. Screenshots under `artifacts/auth_employees_*` and `artifacts/auth_employee_form_*` provide visual QA.

14. **Analyzer.** `flutter analyze`: no issues.

15. **Tests/checks.** `flutter pub get`, `flutter gen-l10n`, `dart run build_runner build --delete-conflicting-outputs`, `dart format .`, `flutter analyze`, `flutter test`: passed. All 356 tests pass. The 40 employee unit/repository/BLoC tests cover CRUD/status, scopes, SQL query composition/order/counts/pagination, seed stability, restart persistence, unique allocation, duplicate/reference/cycle validation, atomic rollback, role ceilings, account access/session revocation/restoration and reactive states. Thirty employee widget tests cover responsive pages, validation, prefill, empty versus filtered-empty, actual create/edit through fields/selectors/date picker, account-pending presentation, filters/search/menu/confirmation, dirty cancel/discard and unauthorized direct routes. Production and explicitly enabled demo release web builds passed, with WASM dry-run compilation. No packages were added in this phase.

16. **Genuine limitations.** New local account credentials/invitations are pending; only the existing five demo fixture identities can authenticate. There is no backend, sender, conflict resolution, password delivery or production account provisioning. Avatar URLs are modeled, but a photo picker is not implemented. References are lightweight seeded catalogs without CRUD. Attendance configuration is read-only/unassigned in Phase 4. Attendance and reports remain shell placeholders. Dashboard snapshots remain the coherent Phase 3 demo dataset (84 company/12 team); replacing only their workforce totals with 25/10 would contradict existing attendance demo counts, so those optional aggregates were not mixed. Native builds, live browser IndexedDB restart testing and assistive-technology certification were not performed; persistence was verified through file-backed SQLite tests and visual QA through Flutter-rendered screenshots.

17. **Phase 5 foundation.** Stable employee IDs/company ownership, typed nullable shift/workLocation/attendancePolicy references, immutable drafts, reusable selections/switches/date/time fields/form grids/details grids/tables/status dialogs, workflow BLoCs, repository validation, explicit grants, modular routes, en/ar resources, schema migration snapshots and transactional outbox are available. Phase 5 can implement separate configuration features and assign active company-owned configuration references without changing the UI/BLoC/repository boundary. No punching, breaks, attendance state machine/history/corrections, reports or unrelated ERP module was implemented in Phase 4.
